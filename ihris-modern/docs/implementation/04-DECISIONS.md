| البند | القيمة |

## 2. وصف الفجوة

النظام الحديث لا يحتوي على نظام تقارير مخصص مثل النظام القديم. لا يوجد جدول تقارير أو صفحات لتقارير مخصصة في النظام الحديث، مما يمنع المستخدمين من إنشاء تقارير مخصصة بناءً على احتياجاتهم.

## ADR-002: تصميم نظام التقارير المخصص (Custom Reports System)

### 2.1 السياق

النظام الحديث لا يحتوي على نظام تقارير مخصص. النظام القديم كان يحتوي على نظام تقارير مخصص مبني على جدول config (نمط key-value) مع أكثر من 13 تقرير معرّف، مع دعم لأنواع عروض متعددة (PieChart, Bar, Scatter, Column, Table) وجداول إحصائية مسبقة الحساب (Zebra Tables). النظام الحديث لا يحتوي على أي جدول أو صفحة أو API للتقارير.

### 2.2 الخيارات التصميمية المطروحة

#### الخيار A: تقارير مبنية على قوالب SQL مُعرّفة مسبقاً + معاملات (Parameterized Templates)

**الوصف:** يتم تعريف التقارير عبر قوالب SQL مكتوبة مسبقاً مع معاملات (parameters) يتم تمريرها من واجهة المستخدم. كل تقرير يحتوي على استعلام SQL ثابت مع إمكانية تمرير معاملات تصفية.

| البند | القيمة |
|-------|--------|
| المرونة | منخفضة - محدودة بالقوالب المُعرّفة مسبقاً |
| الأمان | عالي - الاستعلامات محددة مسبقاً ولا يمكن حقن SQL |
| الأداء | عالي - الاستعلامات محسّنة مسبقاً |
| قابلية الصيانة | متوسطة - يتطلب تعديل الكود لإضافة تقارير جديدة |
| الجهد المقدر | 2-3 أسابيع |
| المخاطر | محدودية في التخصيص قد لا تلبي جميع احتياجات المستخدمين |

##### الخيار B: منشئ تقارير مرئي (Query Builder) مع واجهة drag-and-drop

**الوصف:** واجهة مرئية تسمح للمستخدمين بسحب وإفلات الحقول والعلاقات لبناء تقارير مخصصة بدون كتابة SQL.

| البند | القيمة |
|-------|--------|
| المرونة | عالية جداً - يمكن تخصيص أي حقل وعلاقة |
| الأمان | متوسط - يتطلب تحقق أمني صارم من الاستعلامات المُنشأة |
| الأداء | متوسط - الاستعلامات مُنشأة ديناميكياً قد تكون أبطأ |
| قابلية الصيانة | عالية - لا يتطلب تعديل كود لإضافة تقارير جديدة |
| الجهد المقدر | 6-8 أسابيع |
| المخاطر | تعقيد عالٍ في التنفيذ، مخاطر أمنية عالية في استعلامات المستخدمين |

##### الخيار C: تقارير مبنية على ملفات تعريف (JSON/YAML) مع محرك تنفيذ

**الوصف:** تعريف التقارير عبر ملفات تعريف JSON/YAML تحتوي على استعلامات SQL وأ_settings العرض، مع محرك تنفيذ يقرأ هذه الملفات وينفذ الاستعلامات.

| البند | القيمة |
|-------|--------|
| المرونة | عالية - يمكن تخصيص أي حقل وعلاقة |
| الأمان | متوسط - يتطلب تحقق أمني صارم من الاستعلامات المُنشأة |
| الأداء | عالي - الاستعلامات محددة في ملفات التعريف |
| قابلية الصيانة | عالية - إضافة تقارير جديدة عبر ملفات تعريف فقط |
| الجهد المقدر | 3-4 أسابيع |
| المخاطر | متوسط - يتطلب التحقق من صحة ملفات التعريف |

#### 2.3 التوصية

**الخيار المختار: الخيار C - تقارير مبنية على ملفات تعريف (JSON/YAML) مع محرك تنفيذ**

**المبرر:**
1. يوفر توازناً جيداً بين المرونة والأداء والأمان
2. يسمح بإضافة تقارير جديدة دون تعديل الكود الأساسي
3. يستفيد من هيكل الجداول الديناميكية (EAV) الموجود في النظام الحديث
4. effort معقول (3-4 أسابيع) مقارنة بالخيار B (6-8 أسابيع)
5. أكثر مرونة من الخيار A (2-3 أسابيع) مع جهد معقول

**البدائل المرفوضة:**
- الخيار A: محدود جداً في التخصيص، لا يلبي احتياجات المستخدمين المتقدمة
- الخيار B: معقد جداً، جهد عالي، مخاطر أمنية عالية، يتجاوز المدة المتاحة للسبرنت

#### 2.4 قرارات التصميم

| البند | القرار | التبرير |
|-------|--------|---------|
| تخزين تعريفات التقارير | في قاعدة البيانات (جدول eport_definitions) | يسهل الإدارة عبر واجهة المستخدم ويتيح البحث والاستعلام |
| تخزين ملفات تعريف التقارير (JSON) | في جدول eport_definitions حقل definition (JSONB) | مرونة في إضافة حقول جديدة دون تعديل مخطط القاعدة |
| الأمان: من يستطيع إنشاء تقرير؟ | فقط أدوار admin و hr_manager | تقييد الوصول للوظائف الحساسة |
| الأمان: من يستطيع تشغيل التقرير؟ | جميع المستخدمين المصادق عليهم مع تصفية حسب الصلاحيات | توازن بين الوصول والأمان |
| الأمان: Row-level security | نعم - تطبيق تصفية حسب الصلاحيات على مستوى الاستعلام | منع الوصول للبيانات غير المصرح بها |
| الأداء: استعلامات فورية أم caching؟ | استعلامات فورية مع خيار caching للتقارير الثقيلة | توازن بين الأداء والمرونة |
| صيغ التصدير: الحد الأدنى | JSON و CSV | صيغ أساسية سهلة التنفيذ، يمكن إضافة PDF و Excel لاحقاً |
| الجدولة: تقارير مجدولة الآن أم لاحقاً؟ | لاحقاً (غير مطلوبة في Sprint 1) | غير مطلوبة في المرحلة الأولى، يمكن إضافتها لاحقاً |
| التوافق مع Zebra القديم: ترحيل تعريفات التقارير القديمة تلقائياً؟ أم نعيد إنشاءها يدوياً؟ | يدوي - إعادة إنشاء التقارير المهمة يدوياً | تعريفات التقارير القديمة مخزنة في جدول config كkey-value وتحتاج تحويل يدوي |

#### 2.5 بوابة القرار

**الحالة:**artet (مقبول)

**السبب:** الخيار C يوفر توازناً جيداً بين المرونة والأداء والأمان، ويتماشى مع نمط EAV الموجود في النظام الحديث، والجهد المقدر (3-4 أسابيع) يتوافق مع مدة Sprint 1.

**الخطوة التالية:** الانتقال إلى المرحلة 3 (التنفيذ)
