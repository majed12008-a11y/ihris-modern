## ADR-002: تصميم نظام التقارير المخصص (Custom Reports System)

### 2.1 السياق

النظام الحديث لا يحتوي على نظام تقارير مخصص. النظام القديم كان يحتوي على نظام تقارير مخصص مبني على جدول config (نمط key-value) مع أكثر من 13 تقرير معرّف، مع دعم لأنواع عروض متعددة (PieChart, Bar, Scatter, Column, Table) وجداول إحصائية مسبقة الحساب (Zebra Tables). النظام الحديث لا يحتوي على أي جدول أو صفحة أو API للتقارير.

### 2.2 الخيارات التصميمية المطروحة

#### الخيار A: تقارير مبنية على قوالب SQL مُعرّفة مسبقاً + معاملات (Parameterized Templates)

**الوصف:** يتم تعريف التقارير عبر قوالب SQL مكتوبة مسبقاً مع معاملات (parameters) يتم تمريرها من واجهة المستخدم. كل تقرير يحتوي على استعلام SQL ثابت مع إمكانية تمرير معاملات تصفية.

| البند | القيمة |
|-------|--------|
| المرونة | منخفضة - محدودة بالقوالب المُعرّفة مسبقاً |
| الأمان | عالي - الاستعلامات محددة مسبقاً ولا يمكن حقن SQL |
| الأداء | عالي - الاستعلامات محسّنة مسبقاً |
| قابلية الصيانة | متوسطة - يتطلب تعديل الكود لإضافة تقارير جديدة |
| الجهد المقدر | 2-3 أسابيع |
| المخاطر | محدودية في التخصيص قد لا تلبي جميع احتياجات المستخدمين |

##### الخيار B: منشئ تقارير مرئي (Query Builder) مع واجهة drag-and-drop

**الوصف:** واجهة مرئية تسمح للمستخدمين بسحب وإفلات الحقول والعلاقات لبناء تقارير مخصصة بدون كتابة SQL.

| البند | القيمة |
|-------|--------|
| المرونة | عالية جداً - يمكن تخصيص أي حقل وعلاقة |
| الأمان | متوسط - يتطلب تحقق أمني صارم من الاستعلامات المُنشأة |
| الأداء | متوسط - الاستعلامات مُنشأة ديناميكياً قد تكون أبطأ |
| قابلية الصيانة | عالية - لا يتطلب تعديل كود لإضافة تقارير جديدة |
| الجهد المقدر | 6-8 أسابيع |
| المخاطر | تعقيد عالٍ في التنفيذ، مخاطر أمنية عالية في استعلامات المستخدمين |

##### الخيار C: تقارير مبنية على ملفات تعريف (JSON/YAML) مع محرك تنفيذ

**الوصف:** تعريف التقارير عبر ملفات تعريف JSON/YAML تحتوي على استعلامات SQL وأ_settings العرض، مع محرك تنفيذ يقرأ هذه الملفات وينفذ الاستعلامات.

| البند | القيمة |
|-------|--------|
| المرونة | عالية - يمكن تخصيص أي حقل وعلاقة |
| الأمان | متوسط - يتطلب تحقق أمني صارم من الاستعلامات المُنشأة |
| الأداء | عالي - الاستعلامات محددة في ملفات التعريف |
| قابلية الصيانة | عالية - إضافة تقارير جديدة عبر ملفات تعريف فقط |
| الجهد المقدر | 3-4 أسابيع |
| المخاطر | متوسط - يتطلب التحقق من صحة ملفات التعريف |

#### 2.3 التوصية

**الخيار المختار: الخيار C - تقارير مبنية على ملفات تعريف (JSON/YAML) مع محرك تنفيذ**

**المبرر:**
1. يوفر توازناً جيداً بين المرونة والأداء والأمان
2. يسمح بإضافة تقارير جديدة دون تعديل الكود الأساسي
3. يستفيد من هيكل الجداول الديناميكية (EAV) الموجود في النظام الحديث
4. effort معقول (3-4 أسابيع) مقارنة بالخيار B (6-8 أسابيع)
5. أكثر مرونة من الخيار A (2-3 أسابيع) مع جهد معقول

**البدائل المرفوضة:**
- الخيار A: محدود جداً في التخصيص، لا يلبي احتياجات المستخدمين المتقدمة
- الخيار B: معقد جداً، جهد عالي، مخاطر أمنية عالية، يتجاوز المدة المتاحة للسبرنت

#### 2.4 قرارات التصميم

| البند | القرار | التبرير |
|-------|--------|---------|
| تخزين تعريفات التقارير | في قاعدة البيانات (جدول eport_definitions) | يسهل الإدارة عبر واجهة المستخدم ويتيح البحث والاستعلام |
| تخزين ملفات تعريف التقارير (JSON) | في جدول eport_definitions حقل definition (JSONB) | مرونة في إضافة حقول جديدة دون تعديل مخطط القاعدة |
| الأمان: من يستطيع إنشاء تقرير؟ | فقط أدوار admin و hr_manager | تقييد الوصول للوظائف الحساسة |
| الأمان: من يستطيع تشغيل التقرير؟ | جميع المستخدمين المصادق عليهم مع تصفية حسب الصلاحيات | توازن بين الوصول والأمان |
| الأمان: Row-level security | نعم - تطبيق تصفية حسب الصلاحيات على مستوى الاستعلام | منع الوصول للبيانات غير المصرح بها |
| الأداء: استعلامات فورية أم caching؟ | استعلامات فورية مع خيار caching للتقارير الثقيلة | توازن بين الأداء والمرونة |
| صيغ التصدير: الحد الأدنى | JSON و CSV | صيغ أساسية سهلة التنفيذ، يمكن إضافة PDF و Excel لاحقاً |
| الجدولة: تقارير مجدولة الآن أم لاحقاً؟ | لاحقاً (غير مطلوبة في Sprint 1) | غير مطلوبة في المرحلة الأولى، يمكن إضافتها لاحقاً |
| التوافق مع Zebra القديم: ترحيل تعريفات التقارير القديمة تلقائياً؟ أم نعيد إنشاءها يدوياً؟ | يدوي - إعادة إنشاء التقارير المهمة يدوياً | تعريفات التقارير القديمة مخزنة في جدول config كkey-value وتحتاج تحويل يدوي |

#### 2.5 بوابة القرار

**الحالة:**artet (مقبول)

**السبب:** الخيار C يوفر توازناً جيداً بين المرونة والأداء والأمان، ويتماشى مع نمط EAV الموجود في النظام الحديث، والجهد المقدر (3-4 أسابيع) يتوافق مع مدة Sprint 1.

**الخطوة التالية:** الانتقال إلى المرحلة 3 (التنفيذ)

## ADR-003: سياسة إدارة المستخدمين (User Management Policy)

### 3.1 الحالة

**منفذ (Sprint 2) — قرار بشري ثابت، لا يُعاد الاجتهاد فيه.**

> نطاق التنفيذ: هذه السياسة تحكم GAP-002 (تعديل مستخدم) وGAP-003 (حذف مستخدم).
> نُفِّذت بالكامل في Sprint 2 (فرع `feature/GAP-002-003-user-management`) بعد إغلاق
> GAP-001. التفاصيل التنفيذية في 3.5 وما بعدها، وقد اجتازت بوابة 3.6:
> 12/12 سيناريو قبول + 10/10 أمان + regression 73/73 backend + 3/3 frontend.

### 3.2 القرارات

| البند | القرار |
|-------|--------|
| نوع الحذف | **Soft Delete**: أعمدة `deleted_at`, `deleted_by`, `deletion_reason` |
| من يحذف | دور `admin` **فقط** |
| من يعدّل | `Self` (بياناته الشخصية) + `admin` (أي مستخدم) |
| Self-delete | **ممنوع** |
| مستخدم له سجلات | **ممنوع الحذف** — يُعطَّل (deactivate) مع رسالة خطأ واضحة |
| Purge نهائي | بعد **90 يوماً** — مؤجل إلى **P3** |
| استعادة | خلال **30 يوماً**، `admin` فقط |
| Audit | جدول `user_audit_log (id, user_id, action, changed_by, changed_at, old_values JSON, new_values JSON, reason)` |
| Concurrency | **Optimistic Lock** بحقل `version` |
| الواجهة | صفحة **"المستخدمون المحذوفون"** لـ `admin` |
| Creator | **NOT NULL** — يبقى كما هو |
| التوافق | Soft Delete = **ترقية متعمدة** (النظام القديم كان Hard Delete) |

### 3.3 قواعد التنفيذ الملزمة

1. لا حذف فيزيائي (`DELETE`) لسجلات `users` في مسار التطبيق؛ الحذف = تعيين
   `deleted_at` + `deleted_by` + `deletion_reason`.
2. التحقق من وجود سجلات مرتبطة قبل الحذف؛ عند وجودها يُرفض الطلب برسالة عربية
   واضحة ويُقترح التعطيل بدلاً من الحذف.
3. كل تعديل/حذف/استعادة يكتب صفاً في `user_audit_log` يحوي القيم القديمة والجديدة.
4. كل تحديث يتحقق من `version` المرسل؛ عدم التطابق = تعارض (409) وليس كتابة عمياء.
5. الاستعادة مسموحة فقط خلال 30 يوماً من `deleted_at` ولـ `admin` فقط.
6. Purge بعد 90 يوماً مؤجل إلى P3؛ لا يُنفَّذ الآن.
7. `creatorId` يبقى `NOT NULL`؛ لا يُعاد تصميمه ضمن هذه السياسة.

### 3.4 البدائل المرفوضة

| البديل | سبب الرفض |
|--------|-----------|
| Hard Delete كما في النظام القديم | يفقد قابلية الاستعادة والتدقيق |
| حذف المستخدم مع سجلاته (Cascade) | يدمر تاريخ الموارد البشرية |
| Soft delete بدون audit | لا يلبي متطلبات التتبع |

### 3.5 التفاصيل التنفيذية (Sprint 2)

#### 3.5.1 أعمدة Soft Delete وOptimistic Lock على `users`

| العمود (Prisma / PostgreSQL) | النوع | NULL | الافتراضي | الغرض |
|------------------------------|-------|------|-----------|-------|
| `version` | `INTEGER` | NO | `1` | Optimistic Lock — يزداد بمقدار 1 مع كل كتابة ناجحة |
| `deletedAt` | `TIMESTAMP` | YES | `NULL` | وقت الحذف المنطقي (`NULL` = غير محذوف) |
| `deletedBy` | `INTEGER` | YES | `NULL` | `userId` للمنفّذ (admin) |
| `deletionReason` | `TEXT` | YES | `NULL` | سبب الحذف (1..500 حرف) |
| `restoredAt` | `TIMESTAMP` | YES | `NULL` | وقت آخر استعادة (مطلوب لسيناريو القبول #10) |

> ملاحظة تسمية: قاعدة البيانات الحالية تستخدم camelCase بدون `@map` (مثل `createdAt`،
> `creatorId`)، لذلك أعمدة السياسة `deleted_at/deleted_by/deletion_reason` تُنفَّذ
> فعلياً كـ `deletedAt/deletedBy/deletionReason` مع تطابق كامل في المعنى. الـ API
> يعيد `deletedAt` و`restoredAt` (نفس نمط `createdAt`).

الفهارس: `idx_users_deleted_at` على `("deletedAt")`.

#### 3.5.2 جدول `user_audit_log`

| العمود | النوع | NULL | الافتراضي | ملاحظة |
|--------|-------|------|-----------|--------|
| `id` | `SERIAL` | NO | auto | PRIMARY KEY |
| `userId` | `INTEGER` | NO | — | المستخدم المتأثر (بلا FK: يبقى السجل بعد purge نهائي في P3) |
| `action` | `VARCHAR(20)` | NO | — | `create` \| `update` \| `delete` \| `restore` (CHECK) |
| `changedBy` | `INTEGER` | NO | — | المنفّذ (admin أو المستخدم نفسه) |
| `changedAt` | `TIMESTAMP` | NO | `NOW()` | وقت العملية |
| `oldValues` | `JSONB` | YES | `NULL` | القيم قبل العملية (بلا كلمة المرور أبداً) |
| `newValues` | `JSONB` | YES | `NULL` | القيم بعد العملية (بلا كلمة المرور أبداً) |
| `reason` | `TEXT` | YES | `NULL` | سبب الحذف/التعطيل |

الفهارس: `idx_user_audit_log_user_changed` على `("userId", "changedAt" DESC)`،
`idx_user_audit_log_action` على `("action")`، `idx_user_audit_log_changed_at`
على `("changedAt")`.

**قاعدة صارمة:** لا تُكتب `password` أو أي hash في `oldValues/newValues` مطلقاً.

#### 3.5.3 استراتيجية `version`

1. `version` يبدأ بـ 1 ولا يُرسَل ضمن بيانات التعديل كقيمة تُكتب.
2. كل `PUT` و`DELETE` و`POST /:id/restore` يتطلب `version` (عدد صحيح ≥ 1).
3. التحديث يتم بـ `UPDATE ... WHERE id = ? AND version = ?` داخل معاملة؛
   إن كان عدد الصفوف المتأثرة = 0 → **409 Conflict** وليس كتابة عمياء.
4. عند النجاح: `version = version + 1` مرة واحدة فقط.
5. حقول `version` و`deletedAt/deletedBy/deletionReason/restoredAt` **مرفوضة**
   كمدخلات تعديل (mass assignment) حتى لو أرسلها العميل.

#### 3.5.4 كشف "السجلات المرتبطة" — القرار: A + B

| الخيار | القرار | التبرير بعد فحص FK |
|--------|--------|--------------------|
| **A — فحص مسبق** | ✅ **مختار** | استعلام واحد على `report_definitions.createdBy` و`report_executions.executedBy` يعطي رسالة عربية دقيقة (422) تحوي أسماء/أعداد السجلات وتقترح التعطيل. |
| **B — قيد قاعدة البيانات** | ✅ **مختار كشبكة أمان** | القيود الحالية على الجدولين هي `NO ACTION` وهي ترفض الحذف الفيزيائي عند وجود صفوف مرجعية. لا نستخدم `CASCADE` ولا نحذف السجلات. |
| C — دالة `hasRelatedRecords` قابلة للصيانة | ❌ | تكرار منطق A دون قيمة إضافية؛ A هو التنفيذ الفعلي للدالة. |

**جداول لا تمنع الحذف:** `user_access` (دور المستخدم) و`report_preferences`
(تفضيلات شخصية) — بيانات ملكية داخلية، وتُنظَّف فقط عند purge النهائي (P3).

#### 3.5.5 مصفوفة الصلاحيات

| العملية | admin | مستخدم عادي | غير مصادَق |
|---------|-------|-------------|-------------|
| عرض قائمة المستخدمين | ✅ | ❌ (كما هو حالياً: admin/hr_manager) | 401 |
| عرض مستخدم واحد | ✅ أي مستخدم | ✅ نفسه فقط (غير ذلك 403) | 401 |
| تعديل | ✅ أي مستخدم (بما فيهم نفسه) | ✅ نفسه فقط (غير ذلك 403) | 401 |
| تغيير الدور | ✅ فقط | ❌ 403 (حتى لنفسه — منع تصعيد الصلاحيات) | 401 |
| حذف | ✅ أي مستخدم **عدا نفسه** | ❌ (403، بما في ذلك نفسه) | 401 |
| استعادة | ✅ فقط | ❌ 403 | 401 |
| قائمة المحذوفين | ✅ فقط | ❌ 403 | 401 |

**Self-delete ممنوع دائماً** — حتى للـ admin (403).

#### 3.5.6 عقد الـ API

| الطريقة | المسار | الصلاحية | المدخلات | النجاح |
|---------|--------|----------|----------|--------|
| `GET` | `/api/users/:id` | self أو admin | — | 200 + بيانات المستخدم + `version` |
| `PUT` | `/api/users/:id` | self أو admin | `version`, `firstname?`, `lastname?`, `email?`, `role?` (admin فقط) | 200 + audit `update` |
| `DELETE` | `/api/users/:id` | admin فقط، ليس نفسه | `version`, `reason` (1..500) | 200 + soft delete + audit `delete` |
| `POST` | `/api/users/:id/restore` | admin فقط | `version` | 200 + `restoredAt` + audit `restore` |
| `GET` | `/api/users/deleted` | admin فقط | `page?`, `limit?` | 200 + قائمة المحذوفين + `daysRemaining` |
| `POST` | `/api/users` | admin فقط | الحقول الحالية | 201 + audit `create` |

- أي حقل غير معروف في `PUT`/`DELETE`/`restore` → **400** (رفض mass assignment).
- `version` غير مطابق → **409**.
- بريد غير صالح → **400** برسالة واضحة.
- وجود سجلات مرتبطة → **422** برسالة واضحة.
- استعادة بعد 30 يوماً → **422** "انتهت فترة الاستعادة".
- محاولة تسجيل دخول مستخدم محذوف → **401** (رسالة عامة بلا كشف).

#### 3.5.7 نافذة الاستعادة

`restore` مسموح إذا كان `deletedAt >= NOW() - INTERVAL '30 days'`؛ وإلا 422.
`purge` النهائي بعد 90 يوماً **غير منفَّذ** (P3) ولا يوجد أي مسار أو مهمة له.

### 3.6 البوابة قبل اعتبار ADR-003 "منفذاً"

1. 12/12 سيناريو قبول ناجح على API حقيقي (`ihris_test_gap001`).
2. 8/8 اختبارات أمان (403/401/409/400/422 + SQL injection + mass assignment + IDOR).
3. Regression: backend 42 + frontend 3 + GAP-001 integration 12 ناجحة.
4. Migration idempotent + rollback مُختبر.
5. لا تعديل على `ihris_manage` ولا على `DB export.sql`.

### 4.1 الحالة

### 4.2 القرارات العشرة

| # | البند | القرار | التنفيذ الفعلي |
|---|-------|--------|----------------|
| 1 | لغة الاستعلام | SQL parameterized فقط — لا string concatenation للقيم | كل القيم تمرّ كـ `$1..$n` عبر `$queryRawUnsafe(sql, ...params)`؛ لا تُدمج قيمة واحدة في النص |
| 2 | الجداول المسموح بها | Whitelist صريحة، وأي جدول خارجها مرفوض | `ALLOWED_TABLES` (25 جدولاً) + `isAllowedTable()` + تحقق من وجود الجدول في `information_schema` |
| 3 | المعاملات | Named params (`:param_name`) مع binding آمن | `params: { name: value }` وتُحوَّل إلى `$n`؛ مرجع غير معرّف = خطأ 400 |
| 4 | الحد الأقصى للنتائج | 10,000 افتراضياً، قابل للتجاوز لأدوار محددة | `DEFAULT_MAX_ROWS = 10000`؛ `HARD_MAX_ROWS = 50000`؛ admin يحصل على 50,000 |
| 5 | حد التنفيذ الزمني | 30 ثانية timeout | `SET LOCAL statement_timeout = 30000` داخل معاملة تفاعلية |
| 6 | منع SQL injection | Regex + prepared statements + حد على الحجم | `IDENTIFIER_RE` للمعرّفات، `$n` للقيم، `MAX_FIELDS/MAX_FILTERS/MAX_IN_VALUES/MAX_STRING_LENGTH` |
| 7 | دعم GROUP BY / ORDER BY | نعم، بحدود whitelisted | `groupBy` (أعمدة ضمن `fields`) + `orderBy` (حقول/أسماء تجميعية، `asc|desc`، حتى 5) |
| 8 | تصدير | CSV كامل + JSON كامل + PDF أساسي (pdfkit) | `toCsv()` (UTF-8 BOM، CRLF، quoting) و`toPdf()` عبر `pdfkit`؛ JSON هو نتيجة التنفيذ نفسها |
| 9 | الجدولة | مؤجلة إلى P3 | غير منفّذة |
| 10 | Rate limiting | 10 تنفيذات/دقيقة/مستخدم | `reportExecutionLimiter` على execute وexport (نافذة ثابتة 60 ثانية) |

### 4.3 نموذج تعريف التقرير (JSON)

```json
{
  "table": "people",
  "fields": ["id", "firstname", "surname"],
  "filters": {
    "surname": "مثال",
    "countryId": { "op": "in", "value": [1, 2] },
    "firstname": ":name"
  },
  "params": { "name": "أحمد" },
  "groupBy": ["countryId"],
  "aggregates": [{ "fn": "count", "field": "*", "as": "total" }],
  "orderBy": [{ "field": "id", "dir": "asc" }],
  "limit": 100
}
```

المعاملات المدعومة: `eq, ne, gt, gte, lt, lte, like, ilike, in, isNull`.
الدوال التجميعية: `count, sum, avg, min, max`.

### 4.4 ضمانات الأمان

1. **المعرّفات لا تُعامَل كقيم:** أسماء الجداول/الأعمدة تُتحقق مقابل قائمة ثابتة
   (`ALLOWED_TABLES`) ومقابل `information_schema` الفعلي، ثم تُغلَّف بعلامات تنصيص.
2. **القيم دائماً معامِلات:** حتى `LIMIT` يُمرَّر كـ `$n`.
3. **أعمدة محظورة صراحةً:** `DENIED_COLUMNS = { password }` (موجود في `users` و`people`).
4. **حدود حجم:** 50 حقلاً، 30 فلتراً، 100 قيمة `in`، 500 حرف للقيمة، 5 حقول ترتيب.
5. **التنفيذ في معاملة** مع `statement_timeout` لمنع الاستعلامات المعلّقة.
6. **التحقق مزدوج:** عند الإنشاء (`ReportValidator`) وعند التنفيذ (`ReportEngine.build`)،
   فلا يكفي اختراق صف في قاعدة البيانات لتجاوز الحماية.

### 4.5 القيود المعروفة (مُوثَّقة بصراحة)

| القيد | الأثر | المعالجة |
|-------|-------|----------|
| PDF عبر `pdfkit` لا يشكّل العربية | قد تظهر الحروف العربية متقطعة/معكوسة في PDF | CSV/JSON سليمان؛ معالجة العربية في PDF مؤجلة (تحتاج خطاً + shaping مثل `arabic-persian-reshaper` + `bidi`) |
| Rate limit في الذاكرة | لا يعمل عبر عدة نسخ Node | مطلوب مخزن مشترك (Redis) عند التوسع الأفقي |
| `truncated` قد تكون `true` عند تساوي عدد الصفوف مع `limit` | إنذار زائف محتمل | مقبول حالياً؛ يمكن استعلام `limit + 1` لاحقاً |
| لا دعم JOIN صريح | التقارير على جدول واحد | مؤجل؛ يتطلب تعريف علاقات whitelisted |
| لا RLS على مستوى الصف | التصفية حسب الصلاحيات غير مطبقة في المحرك | مؤجلة إلى مرحلة الصلاحيات |

## ADR-005: إبطال رموز JWT عبر `tokenVersion`

### 5.1 الحالة

**مُنفَّذ في Sprint 2.5** (فرع `feature/sprint-2.5-hardening`) — أغلق ثغرة بقاء
الرموز صالحة بعد الحذف/التعطيل/تغيير الدور.

الملفات:

- `backend/src/middleware/auth.ts` — تحقق DB لكل طلب

- `migrations/pending/004_user_token_version.sql` + rollback

### 5.2 التصميم

| البند | القرار |
|-------|--------|
| الحقل | `users.tokenVersion INTEGER NOT NULL DEFAULT 1` |
| محتوى JWT | `{ userId, username, role, tokenVersion, iat, exp }` |
| التحقق | بعد `jwt.verify` يُقرأ المستخدم من DB: يجب `jwt.tokenVersion === user.tokenVersion` |
| الحذف المنطقي | `tokenVersion++` |
| التعطيل | `tokenVersion++` |
| تغيير الدور | `tokenVersion++` |
| التفعيل | بدون زيادة (الرموز القديمة مبطلة أصلاً) |
| الاستعادة | بدون زيادة (أُبطلت عند الحذف) |
| حالات الرفض | مستخدم محذوف / معطّل / نسخة غير مطابقة → **401** |
| مصدر الدور | DB وليس الـ JWT (يسري تغيير الدور فوراً) |

### 5.3 المزايا

1. **إبطال فوري** بلا انتظار انتهاء صلاحية الرمز.
2. **بلا بنية تحتية إضافية** — لا Redis ولا قائمة إبطال.
3. **بسيط وقابل للتدقيق** — عمود واحد + مقارنة واحدة.
4. **يغطي الحذف والتعطيل وتغيير الدور** في مسار واحد.

### 5.4 القيود (مُوثَّقة بصراحة)

| القيد | الأثر |
|-------|-------|
| استعلام إضافي لكل طلب مصادَق | قراءة بالمفتاح الأساسي (`id`) — تكلفة منخفضة ومقبولة |
| لا إبطال لكل جهاز | إبطال كل الرموز معاً؛ لا يمكن طرد جهاز واحد فقط |
| الرموز الصادرة قبل النشر بلا `tokenVersion` | تُرفض (401) — سلوك مقصود وآمن |
| يعتمد على DB في كل طلب | تعطّل DB يمنع المصادقة (مقبول) |

### 5.5 متى نرقّي إلى Refresh Tokens؟

مؤجل إلى **P3**، ويصبح مطلوباً إذا احتجنا:
- إبطالاً لكل جهاز/جلسة على حدة،
- جلسات طويلة مع تدوير الرموز،
- تخفيف الحمل عن DB (تخزين حالة الجلسة).

### 5.6 بوابة القرار

### 7.3 تفاصيل الحماية من الحذف

### 7.4 التفرد (Uniqueness)

- `countries.name` و`countries.code`: UNIQUE في DB + تحقق تطبيقي case-insensitive → **409**.

  (سيناريو القبول 9 يطلب ذلك). `jobs.code` لا يُفرض تفرّده (لا دليل في القديم).
