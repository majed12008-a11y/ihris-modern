# جاهزية ترحيل البيانات (Data Migration Readiness)

## 1. نظرة عامة

توضح هذه المرحلة إمكانية نقل البيانات من النظام القديم (iHRIS Legacy MySQL) إلى النظام الحديث (IHRIS Modern PostgreSQL). هذا التحليل تحليلي فقط ولا يتضمن تنفيذ أي عملية ترحيل.

## 3. تحديات ترحيل البيانات

### 3.1 تحديات أنواع البيانات

| النوع القديم | النوع الحديث | التحدي | الحل المقترح |
|-------------|-------------|-------|-------------|
| `int(11)` | `Int` | لا تحدي | تحويل مباشر |
| `int(10) unsigned` | `Int` | لا تحدي | تحويل مباشر |
| `tinyint(3) unsigned` | `Int` | لا تحدي | تحويل مباشر |
| `tinyint(4)` | `Int` | لا تحدي | تحويل مباشر |
| `varchar(20)` | `String (@db.VarChar(30))` | لا تحدي | تحويل مباشر |
| `varchar(50)` | `String (@db.VarChar(255))` | لا تحدي | تحويل مباشر |
| `varchar(100)` | `String (@db.VarChar(255))` | لا تحدي | تحويل مباشر |
| `varchar(255)` | `String (@db.VarChar(255))` | لا تحدي | تحويل مباشر |
| `text` | `String` | لا تحدي | تحويل مباشر |
| `text utf8` | `String` | لا تحدي | تحويل مباشر |
| `datetime` | `DateTime` | لا تحدي | تحويل مباشر |
| `longblob` | `Bytes` | لا تحدي | تحويل مباشر |
| `char(32)` | `String` | لا تحدي | تحويل مباشر |
| `boolean` | `Boolean` | لا تحدي | تحويل مباشر |

### 3.2 تحديات المفاتيح والمعرفات

| التحدي | الوصف | الحل المقترح |
|--------|-------|-------------|
| معرفات تلقائية (auto_increment) | كلا النظامين يدعم auto_increment | تحويل مباشر مع إعادة تعيين المعرفات |
| مفاتيح خارجية (Foreign Keys) | العلاقات بين الجداول يجب الحفاظ عليها | ترحيل الجداول المرجعية أولاً ثم الجداول التابعة |
| مفاتيح أساسية مركبة | جدول `last_entry` لديه مفتاح أساسي مركب [recordId, formFieldId] | الحفاظ على نفس البنية في النظام الحديث |

### 3.3 تحديات البيانات الديناميكية (EAV)

| التحدي | الوصف | الحل المقترح |
|--------|-------|-------------|
| كميات كبيرة من البيانات | جدول `entry` يحتوي على عدد كبير من السجلات | ترحيل دفوعياً (batch) مع معالجة الدفعات الصغيرة |
| سلامة العلاقات | العلاقات بين `record`, `entry`, `form_field` يجب الحفاظ عليها | ترحيل في الترتيب الصحيح: form → field → form_field → record → entry |
| الأداء | ترحيل كميات كبيرة من البيانات قد يستغرق وقتاً طويلاً | استخدام أدوات批量 الإدراج (bulk insert) |

### 3.4 تحديات كلمات المرور

| التحدي | الوصف | الحل المقترح |
|--------|-------|-------------|
| تشفير MD5 | كلمات المرور في النظام القديم مخزنة بـ MD5 hash | لا يمكن تحويل MD5 إلى bcrypt مباشرة، يجب إعادة تعيين كلمات المرور للمستخدمين |
| نقص salt | MD5 في النظام القديم لا يستخدم salt | إعادة تعيين كلمات المرور للمستخدمين عند تسجيل الدخول الأول |

## 5. أدوات الترحيل المقترحة

| الأداة | الوصف | المزايا | العيوب |
|--------|-------|-------|---------|
| سكريبت SQL مخصص | كتابة سكريبت SQL لنقل البيانات من MySQL إلى PostgreSQL | بسيط، لا يتطلب أدوات إضافية | يتطلب كتابة كود يدوي، قد يكون عرضة للأخطاء |
| أداة pgloader | أداة مفتوحة المصدر لترحيل البيانات من MySQL إلى PostgreSQL | سريعة، تدعم批量 الإدراج، تتعامل مع أنواع البيانات تلقائياً | يتطلب تثبيت أداة إضافية، قد تحتاج إلى تعديل الإعدادات |
| سكريبت Node.js + Prisma | كتابة سكريبت باستخدام Prisma Client لنقل البيانات | متكامل مع النظام الحديث، يدعم التحقق من صحة البيانات | أبطأ من pgloader، يتطلب تطوير كود |
| أداة MySQL Workbench | أداة رسمية من MySQL لنقل البيانات | سهلة الاستخدام، واجهة رسومية | قد لا تدعم جميع الميزات، قد تكون بطيئة للبيانات الكبيرة |

## 6. خطة الاختبار بعد الترحيل

| الاختبار | الوصف | المعايير المقبولة |
|---------|-------|-----------------|
| اختبار عدد السجلات | مقارنة عدد السجلات في كل جدول بين النظامين القديم والحديث | عدد السجلات يجب أن يتطابق |
| اختبار سلامة البيانات | مقارنة عينة من البيانات بين النظامين القديم والحديث | البيانات يجب أن تكون متطابقة |
| اختبار العلاقات | التحقق من صحة العلاقات الخارجية بين الجداول | جميع العلاقات الخارجية يجب أن تكون صالحة |
| اختبار الأداء | قياس وقت استعلام البيانات في النظام الحديث | وقت الاستجابة يجب أن يكون مقبولاً |
| اختبار واجهة المستخدم | التحقق من ظهور البيانات بشكل صحيح في واجهة المستخدم | البيانات يجب أن تظهر بشكل صحيح |
